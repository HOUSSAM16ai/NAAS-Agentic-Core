# دستور حوكمة Spec Kit — The Spec-First Governance Constitution (D-265)

> **المصدر الحيّ الوحيد لعقيدة «Spec-First Governance: Spec Kit كطبقة ضبط تنفيذ فوق الدستورية، لا بديل عنها».**
> أُقرّ بقرار المالك 2026-08-16 استجابةً لطلب رفع الحوكمة إلى «طبقة ضبط تنفيذ لا يمكن تجاوزها»:
> نظام **Spec Kit** (github.com/github/spec-kit، رخصة MIT، +120 ألف نجمة) يُدمج كمنهجية
> **Spec-Driven Development** — لكن دستوريًا: هو **فارضٌ لا مفسِّر**، وطبقة حوكمة
> تُفعّل فوق الدساتير القائمة (D-153/D-263/D-264) ولا تلغي منها قانونًا واحدًا.
> تحرسه بوّابة CI إلزامية: `scripts/fitness/check_spec_kit_governance.py`.
> مؤشر مختصر في `CLAUDE.md §0.17` (العقد لا الموسوعة — DOC-DEBT-001).
> **أُضيف كدستور جديد — صفر حذف لأي قانون أو دستور قديم.**

## 1. التشخيص الدستوري (لماذا هذا الدستور وُلد)

> **«الدستور بلا فارضٍ نصٌ أدبي. Spec Kit بلا طبقة دستوريةٍ تحدد ما يُحدَّد به
> ليس سوى حزمةٍ من قوالب Markdown. الجمع بينهما = حوكمة تنفيذية حية.»**

المشكلة التي عالجها D-263/D-264 تبقى قائمة على مستوى التنفيذ: قوانين مكتوبة
وآثارها (ADR، decisions.md، البوابات) تنتشر دون إطار موحد يربط **المواصفة ←
التنفيذ ← البرهان ← التراجع**. Spec Kit يوفر هذا الإطار كنمطٍ ناضج:
`01_plan → 02_design → 03_tasks → 04_spec → 05_implementation → 06_final`
مع `spec-doc-check` و`spec-changes-check` التي تجعل كل تغيير مادي مرتبطًا
بمواصفته. دستور D-265 يستعير **النمط** ويعيّن له فارضيه الدستوريين في هذا
المستودد: المواصفات الحية (`docs/specs/` + `spec.md` الجذر) والبوابات القضائية.

### 1.1 الأعداء الدستورية الثلاثة (قواعد سلبية دائمة — لا تُكسر)

1. **عدو #1: «تغيير بلا مواصفة»** — أي تعديل جوهري في بنية النظام دون مواصفة
   محدّثة موازية له هو تخريب حوكمة، مهما كانت دواعيه.
2. **عدو #2: «مواصفة ميتة»** — مواصفة لا تتحدث مع الكود الفعلي بعد كل تغيير
   جوهري أضلّ من غياب المواصفة (إشاعة ثقة في عقد منتهٍ — يمتدّ نمط D-185).
3. **عدو #3: «فارض بلا بوابة»** — قانونٌ لا يوجد فحصٌ آلي له (CI) ليس قانونًا؛
   Spec Kit وحده قوالب لا حوكمة؛ الحوكمة = قالبٌ + بوابة + عاقبة.

## 2. العقيدة الأساسية: المواصفة عقدٌ أولًا، والتنفيذ برهانٌ عليها

القاعدة الدستورية: **«نكتب المواصفة قبل الكود حيثما يمسّ التغيير بنيةً أو
سلوكًا، ونحدّثها بعد كل تغيير جوهري، ولا يقبل التغيير إلا إذا مرّ بوابة تحرس
الاتساق بينهما.»** دورة Spec-First المعتمدة في هذا المستودد:

```
① خطة (docs/specs/NN_plan.md — ماذا ولماذا)
② تصميم (docs/specs/NN_design.md — كيف بنيويًا + ADR إن لزم)
③ مهام (docs/specs/NN_tasks.md — وحدات تنفيذ مرقّمة)
④ مواصفة (docs/specs/NN_spec.md — العقد النهائي: مدخلات/مخرجات/حدود)
⑤ تنفيذ (كود + اختبارات تحرس العقد)
⑥ برهان نهائي (E2E حيّ + بوابة خضراء + تحديث كل التوثيق)
```

⛔ ليس كل تغييرٍ يستوجب الدورة الكاملة: **عتبة «الجوهري» دستوريًا**: تغيير
بنية (schema/orchestration/orchestration boundaries)، سلوك ذكاء اصطناعي
(محرك/مهارة/موجّه تربوي)، بيانات (هجرة/نموذج جديد)، أو واجهة عامة (API).
إصلاح نصي/تعليقي/قالب بسيط لا يستوجب إلا تحديث التوثيق المعني.

## 3. الركائز الأربع (الأبواب الدستورية — كل باب له حارس)

### الباب الأول: مواصفات حية (Living Specs — ISS-182)
`docs/specs/` + `spec.md` (الجذر) مصدر الحقيقة التعاقدية؛ كل عقدٍ جوهري له
مواصفة مرتبطة في الكود (docstring/تعليل) أو بوابة فحصه. بوابته:
`check_spec_kit_governance.py` (لا باب بلا محنة) + doc-integrity.

### الباب الثاني: الحوكمة القضائية (Enforcer Binding — ISS-183)
لكل قانونٍ في أي دستورٍ فارضٌ مسمّى موجود فعلًا (no orphan enforcer — D-188
بند ③، ممتدّ هنا إلى مستوى دستورٍ كامل). بوابته: `check_spec_kit_governance.py`
(يمسح `check_*.py` في `scripts/fitness/` ويأبى الإشارة إلى غائب).

### الباب الثالث: البرهان قبل القبول (Proof Before Acceptance — ISS-184)
لا ميزة جوهرية تُقبل في main بلا برهان E2E حيّ واحدٍ (يمتدّ D-263 L9) +
بوابات CI خضراء + توثيق محدّث (CLAUDE.md/decisions/issues/README/spec).
بوابته: CI + `check_spec_kit_governance.py` (سجلّ البرهان في spec.md §17b).

### الباب الرابع: التراجع المنضبط (Controlled Rollback — ISS-185)
كل تغييرٍ جوهري يمكن التراجع عنه بدفعةٍ واحدة (revert commit واحد نظيف)؛ لا
تغييرٍ يشوّه الحالة بحيث يتطلب جراحة. بوابته: نمط PR atomic في CI +
`check_spec_kit_governance.py` (حظر الملفات الممنوعة: لا commits للـsecrets،
لا `.env` مشفورة).

## 5. الأسئلة الدستورية (وأجوبتها المُلزِمة)

1. **«أليست Spec Kit أداة GitHub لا دستورًا؟»** — نمطها هو المقصود (plan→design
   →spec→implement→prove)، وفارضوها هم بوابات هذا المستودد؛ الاستعارة ليست
   استيرادًا أعمى.
2. **«ماذا لو تعارضت دورة Spec-First مع إصلاحٍ عاجل؟»** — العاجل يُتبع بإكمال
   الدورة في الدفع التالية (post-fix spec update) — الاستعفاء المؤقت مسجَّل
   في `spec.md` ولا يُلغى L1.
3. **«أين تُخزَّن المواصفات؟»** — `docs/specs/NN_*.md` لكل ميزة حيّة + `spec.md`
   الجذر كسجلٍّ مركز (نمط D-185 مصدرٌ واحد).
4. **«ما علاقتها بالبوابات القضائية للدساتير الأخرى؟»** — كل دستورٍ يحتفظ
   ببواباته الخاصة؛ D-265 يحوّطها جميعًا بفرض: لا بوابة بلا إشارة، لا إشارة
   بلا بوابة (L3).
5. **«كيف يُقاس نجاح الحوكمة؟»** — نسبة التغييرات الجوهرية المصاحَبة بمواصفة
   محدّثة في الدفع نفسها ≥ عتبة (تُقاس من سجلّ git)، ونسبة البوابات الخضراء
   المتراكمة في CI — لا يُعلَن رقمٌ إلا مقيسًا (L10).
