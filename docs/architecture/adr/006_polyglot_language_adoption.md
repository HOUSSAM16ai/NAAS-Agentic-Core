# ADR-006 — تبنّي اللغات متعدّدة (Polyglot) عبر العقد لا عبر الرغبة

- **الحالة:** مقبول (D-185 — 2026-07-28)
- **السياق المُحرِّك:** توصية خارجية باعتماد ترتيب لغات مستقبلي
  (TypeScript · Rust · Go · WebAssembly · Kotlin · Julia · Elixir · Scala · C/C++ · Mojo)،
  ومطلب المالك: «تبنٍّ حقيقي **عند الحاجة** + توثيق الكل».

---

## 1. السياق

المستودع اليوم لغتان فقط: **Python** (المونوليث + 13 خدمة مصغّرة) و**JavaScript**
(واجهة Next.js). ودستور الخدمات المصغّرة (`docs/architecture/MICROSERVICES_CONSTITUTION.md`،
القاعدة 3) يُجيز صراحةً **Polyglot & Containerized**: «استعمل الأداة الأنسب للمهمّة، معزولةً
في Docker».

لكن `docs/architecture/EXTENSION_SEAMS.md` يُرسي قاعدة مضادّة للتضخّم: **لا تُضاف تقنية بلا
مقعد ومستهلك حيّ** — والقدرة بلا مستهلك حيّ تُحذَف لا تُترَك stub (درس Kagent، D-173).
فالسؤال ليس «هل نستطيع؟» بل «ما شرط التبنّي الذي يمنع عشر سلاسل أدوات ميتة؟».

## 2. القرار

**اللغة تدخل النظام من باب العقد لا من باب الحماس.**

1. **الحدّ هو العقد لا اللغة.** كل بوّابات المشروع التي تحكم الخدمات المصغّرة —
   `check_openapi_parity.py` · `check_ports_consistency.py` · `check_service_catalog_parity.py`
   — تفحص **عقد OpenAPI + `/health` + `/metrics` + منفذاً في السجلّ**، ولا تفحص اللغة
   إطلاقاً. فأي خدمة بأي لغة تلتزم هذه الأربعة تدخل النظام بلا تعديل بوّابة واحدة.

2. **شرط التبنّي (يجب أن تتحقّق الثلاثة معاً):**
   - **عبء عمل حقيقي مقيس** يعجز عنه Python/TypeScript (زمن استجابة، توازٍ، ذاكرة، أمان نوعي).
   - **عقد مُلتزَم** في `docs/contracts/openapi/` قبل أول سطر منطق.
   - **برهان ثلاثي حيّ** (import + call chain + runtime evidence) قبل إعلانها ACTIVE — وإلا
     فهي DORMANT بالاسم الصريح (CLAUDE.md §6.6).

3. **يُتبنّى الآن: TypeScript فقط** — لأنه وحده يملك حاجة مُثبَتة اليوم (§4).
   والتسع الباقيات تُوثَّق **كمقاعد** في `EXTENSION_SEAMS.md §7` بشرط تبنٍّ لكلٍّ،
   **بلا سطر كود واحد** حتى يتحقّق شرطها.

4. **مقياس النجاح ثابت.** أي لغة تُضاف تخدم «فجوة الوهم» (الأداء المدعوم − القدرة غير
   المدعومة المؤجَّلة). لغة لا تُقلّص هذه الفجوة ولا تُقلّص كلفة تشغيل ⇒ مرفوضة.

## 3. البرهان العملي: `notation-service`

خدمة D-185 (`microservices/notation_service/`, :8011) هي **المثال المرجعي** لهذه القاعدة:
سطحها كلّه عقد (`/resolve` · `/define` · `/symbols` · `/health` · `/metrics`)، وبيانات
منطقها جدول حتمي، وصفر اعتماد على المونوليث. فتنفيذ بديل بـRust أو Go يلتزم
`docs/contracts/openapi/notation_service-openapi.json` **يستبدلها كاملةً بلا لمس العقل
التربوي ولا أي بوّابة** — وهذا هو الاختبار الحقيقي لادّعاء «API-first».

## 4. لماذا TypeScript الآن دون غيره

الواجهة كانت JavaScript صرفاً: لا `tsconfig.json`، ولا `@types/*`، و**عقود OpenAPI الـ13
غير مُستهلَكة منها إطلاقاً**. فكل حقل يُقرأ نصّياً، وأي انحراف في عقد خدمة لا يظهر إلا في
متصفّح الطالب. هذه فجوة عقدية حقيقية تجعل «API-first» صحيحاً في الخلفية ووهماً عند الحافة.

**ما نُفِّذ فعلاً (D-185) — المرحلة الأولى: طبقة تحقّق العقود.**
`scripts/contracts/generate_frontend_types.py` يولّد `frontend/types/api.d.ts` (124 نوعاً) من
العقود الـ13 المُلتزَمة، ويُفحَص بـ`tsc -p tsconfig.check.json` (بـ`strict` و`skipLibCheck:false`)
عبر بوّابتين في وظيفة `frontend-tests`: تطابق الملف المُولَّد مع العقود، ثم فحص الأنواع.
البوّابة أثبتت قيمتها فوراً: كشفت أن الإحالات (`$ref`) كانت تُولَّد بلا بادئة الخدمة فتشير إلى
أنواع غير موجودة — عطبٌ حقيقي في المولِّد أُصلح.

**قيد بيئي صريح — ولماذا لم نُحوِّل كود الواجهة بعد.** `next build` يُفعِّل مسار TypeScript
تلقائياً حالما يرى `tsconfig.json` أو أي ملف `.ts` داخل `app/`، ويشترط حينها
`typescript` + `@types/node` + `@types/react` كـ**تبعيات حقيقية** — أي تعديل
`package-lock.json`. (تحقّق حيّ: `next build` فشل بـ«Please install @types/node».)
توليد القفل يتطلّب `npm install` وهو **محجوب في بيئة التطوير الحالية**، ولذلك:
- الملف مُسمّى `tsconfig.check.json` **عمداً** (لا `tsconfig.json`) فلا يلتقطه Next.
- الأنواع تعيش في `frontend/types/` خارج مسارات مصدر Next.
- سلسلة الأدوات تُجلَب عند الطلب (`npx`) فيبقى `package-lock.json` ثابتاً بايتاً ببايت
  ولا يمكن أن ينحرف `npm ci`.

**المرحلة الثانية (خطوة واحدة، متى توفّرت الصلاحية):**
`npm i -D typescript @types/node @types/react` ⇒ التزام `package-lock.json` ⇒ إعادة تسمية
`tsconfig.check.json` إلى `tsconfig.json` ⇒ تحويل الوحدات ملفاً ملفاً (بدءاً بـ`wsUrl.js`).
**لا يُدّعى أن كود الواجهة صار TypeScript** — الحاصل اليوم أن **العقود صارت أنواعاً مُتحقَّقة
في CI**، وهي الفجوة الحقيقية التي كانت مفتوحة.

## 5. العواقب

**إيجابية:** انحراف العقد صار خطأ ترجمة في CI لا مفاجأة عند الطالب · الحدّ صار العقد فأي لغة
مستقبلية تدخل بلا تعديل بوّابة · شرط التبنّي مكتوب فلا نقاش ذوقي لاحقاً.

**سلبية مقبولة:** التبنّي على مرحلتين، فالمرحلة الأولى تُعطي **تحقّق العقود** لا هجرة الكود —
تُذكَر صراحةً ولا يُدّعى غيرها · `npx` يضيف ثواني إلى وظيفة CI مقابل ثبات القفل ·
`api.d.ts` مُولَّد ويجب إعادة توليده مع كل تغيير عقد — تحرسه بوّابة `--check` · اسم
`tsconfig.check.json` غير مألوف ويحتاج تعليقاً (موجود داخل الملف وفي `package.json`).

**المرفوض صراحةً:** إضافة عشر خدمات «Hello World» بعشر لغات لإثبات القدرة على تعدّد اللغات.
ذلك عشر سلاسل أدوات وعشر صور Docker وعشر مصادر انحراف — بلا مستهلك واحد. هذا بالضبط ما
تمنعه قاعدة Kagent (D-173).

## 6. البدائل المرفوضة

| البديل | لماذا رُفض |
|--------|------------|
| خدمة عاملة بكل لغة من العشر | كود ميت بلا مستهلك؛ يخالف YAGNI ودرس Kagent؛ يُضخّم CI عشرة أضعاف |
| توثيق فقط بلا أي تبنٍّ | يترك فجوة الواجهة العقدية الحقيقية مفتوحة؛ و«API-first» يبقى وهماً عند الحافة |
| تحويل الواجهة كاملةً إلى TS دفعة واحدة | تغيير ضخم غير قابل للعكس، يخلط هجرة لغة بإصلاح تربوي في PR واحد |
| TypeScript كـ`devDependency` الآن | يتطلّب توليد `package-lock.json` عبر `npm install` وهو محجوب في بيئة التطوير الحالية؛ التزام قفل مكتوب يدوياً بلا تحقّق integrity خطر أكبر من التأجيل |
